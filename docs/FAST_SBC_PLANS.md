# 빠른 SBC 제출안 설계

## 목표

기존 `Completion(n)`은 버튼을 누르는 즉시 선수를 다시 검색하고 한 번의 SBC를 제출한다. 새 동작은 제출과 선별을 분리한다.

```text
Completion
  → 제출안 생성
  → 최대 10개 목록 검토
  → 좌우 버튼으로 회차 이동
  → 현재 화면의 제출안만 제출
```

한 번에 열 개를 자동 제출하지 않는다. 사용자가 각 제출안의 선수를 확인하고 현재 안을 명시적으로 제출해야 한다.

## 제출안 개수

- 생성 상한은 10개다.
- 완전하게 채울 수 있는 제출안만 저장한다.
- 10개를 시도할 수 없으면 9, 8, 7 순서로 목표 개수를 낮춰 다시 배정한다.
- 마지막에 인원이 부족한 부분 제출안은 표시하지 않는다.
- `Completion` 가능 횟수 계산은 전체 제출 화면에서 `Math.floor`를 사용한다.
- 미할당 중복 선수 화면은 한 장의 중복 선수로도 빠른 SBC 진입점을 보여야 하므로 기존 `Math.ceil` 동작을 유지한다.

## 선수 배정과 중복 규칙

서로 다른 식별자를 다른 범위에서 사용한다.

| 식별자 | 적용 범위 | 목적 |
|---|---|---|
| `item.id` | 모든 제출안 | 동일한 실물 카드를 둘 이상의 회차에 사용하지 않음 |
| `databaseId` | 한 제출안 내부 | 같은 선수의 다른 카드 버전이 같은 스쿼드에 들어가지 않음 |

SBC Storage에 동일 선수 카드가 두 장 있고 `item.id`가 서로 다르면 각각 다른 회차에 사용할 수 있다. 반대로 같은 `item.id`는 화면상 다른 조건을 만족하더라도 한 번만 예약한다.

후보에는 기존 빠른 SBC 보호 규칙을 적용한다.

- 잠금 선수 제외
- 사용자 지정 리그·희귀도 제외
- 거래 불가 우선 설정
- 대여, 진화 등록, 기간 제한 선수 제외
- 현재 활성 스쿼드 선수 제외
- 미할당 중복 선수에 대응하는 클럽 카드를 우선 배치
- SBC Storage 우선 설정 반영

기존 `getItemBy()`의 `firststorage` 처리는 `databaseId` 기준으로 후보를 하나만 남긴다. 제출안 생성에서는 서로 다른 실물 복사본을 다음 회차에 사용할 수 있도록 해당 중복 제거만 건너뛰고, Storage 우선순위는 별도 정렬로 적용한다.

## 배정 알고리즘

요구 조건별 후보를 만든 뒤 후보가 부족한 제한 조건부터 처리한다. 한 회차씩 전부 채우는 방식은 첫 회차의 넓은 조건이 다음 회차에 필요한 희귀 후보를 가져갈 수 있으므로, 모든 목표 회차를 함께 배정한다.

```text
목표 회차 N 결정
  → N개의 빈 제출안 생성
  → 제한적인 조건부터 처리
  → 조건 슬롯마다 후보가 가장 적은 회차를 먼저 선택
  → 다른 조건에도 필요한 databaseId는 뒤로 배치
  → item.id를 전체 회차 예약 집합에 추가
  → 한 회차라도 완성되지 않으면 N-1로 재시도
```

이 방식은 다음 사례를 처리한다.

- 희귀 1명과 동일 품질 나머지처럼 후보 조건이 겹치는 경우
- 동일 선수의 서로 다른 실물 복사본을 다른 회차에서 사용하는 경우
- 서로 다른 조건 후보가 같은 `databaseId`를 공유하는 경우
- 총 후보 수는 충분하지만 한 회차의 동일 선수 중복 때문에 배정이 실패하는 경우

## 제출안 세션

생성 결과는 메모리의 제출안 세션에 보관한다.

```text
FastSbcPlanSession
  ├─ setId / challengeId
  ├─ estimatedCount
  ├─ requiredCount
  ├─ currentIndex
  ├─ submitting
  └─ plans[]
       ├─ number
       ├─ status: ready | submitting | submitted | invalid
       ├─ itemIds[]
       ├─ players[]
       └─ snapshots[]
```

팝업을 닫거나 보상 화면이 표시되어도 같은 SBC의 준비된 제출안은 세션에 남는다. 보상 화면의 `Again` 버튼은 준비된 제출안이 있으면 즉시 재선별하지 않고 제출안 화면으로 돌아간다.

## 정확한 제출과 재검증

제출 버튼은 현재 보이는 안의 `itemIds`를 그대로 사용한다. 제출 시점에 `getItemBy()`로 선수를 새로 선정하지 않는다.

1. Club과 SBC Storage에서 저장된 모든 `item.id`를 다시 찾는다.
2. 사라진 카드, 회차 간 중복, 회차 내부 `databaseId` 중복을 검사한다.
3. 최신 SBC Challenge를 다시 불러온다.
4. 저장된 선수 객체만 `playerListFillSquad()`에 전달한다.
5. `challenge.canSubmit()`을 다시 검사한다.
6. 검증된 현재 안만 EA 제출 서비스로 보낸다.

선수가 이동·소모되어 찾을 수 없거나 요구사항이 바뀌면 해당 안은 `invalid`가 되고 제출 버튼이 비활성화된다. `Regenerate Plans`로 현재 재고에서 다시 계산할 수 있다. 제출 요청 중에는 좌우 이동, 재생성, 제출 버튼을 모두 비활성화해 이중 탭을 막는다.

## UI 구조

```text
┌──────────────────────────────────┐
│ Fast SBC Plans               [×] │
│ Daily Silver Upgrade             │
│ 184 estimated · 10 plans created │
├──────────────────────────────────┤
│ [‹]        Plan 1 of 10       [›]│
│ Ready · 11 players · no duplicates│
├──────────────────────────────────┤
│ 01  74  Player name      Storage │
│         CM · Common · Untradeable│
│ 02  73  Player name         Club │
│         ST · Rare · Untradeable  │
│ ...                              │
├──────────────────────────────────┤
│ [ Regenerate Plans ]             │
│ [       Submit Plan 1       ]    │
└──────────────────────────────────┘
```

- 선수 카드는 렌더링하지 않고 텍스트 행을 사용한다.
- 각 행은 순번, OVR, 이름, 포지션, 희귀도, 거래 상태, 저장 위치를 표시한다.
- 모바일은 화면 가장자리에서 6px 여백을 둔 전체 높이 팝업이다.
- 헤더와 하단 작업 영역은 고정되고 선수 목록만 스크롤된다.
- 닫기 버튼과 좌우 버튼은 최소 40~44px 터치 영역을 사용한다.
- 데스크톱 팝업 폭은 최대 640px다.
- 제출안 화면은 EA 네이티브 대화상자 내부에 중첩하지 않고 `document.body`에 독립 모달 오버레이로 렌더링한다.
- 경고 대화상자의 종료 이벤트가 끝난 다음 이벤트 턴에 제출안 오버레이를 열어 Android Edge의 레이어 교체 충돌을 방지한다.
- 오버레이는 닫기 버튼, 바깥 영역 탭, `Escape` 키로 닫을 수 있다.

## 연결된 진입점

다음 `Completion` 버튼은 모두 제출안 화면을 연다.

- SBC 요구사항 화면의 빠른 완료 버튼
- SBC 상세 화면 상단 빠른 버튼
- 단일 Challenge SBC 타일
- 다중 Challenge 목록의 각 빠른 완료 버튼

미할당 중복 선수 화면의 빠른 작업 버튼은 기존 즉시 처리 경로를 유지한다. 이 버튼은 특정 중복 선수를 처리하기 위한 별도 흐름이며 `Completion` 미리보기 진입점이 아니다.

## SBC 데이터 로딩

제출안 미리보기와 실제 제출의 데이터 로딩 책임을 분리한다.

- 미리보기는 현재 화면에 이미 로드된 Challenge를 우선 사용한다.
- 캐시된 Challenge가 없으면 EA의 Challenge 목록과 상세 데이터를 요청한다.
- EA Web App 버전에 따라 Challenge 목록이 `data.challenges`, `response.challenges`, 최상위 `challenges` 또는 배열로 반환되는 경우를 모두 처리한다.
- 목록 응답의 `success` 필드가 생략되더라도 SBC repository가 정상 갱신됐다면 성공으로 처리한다.
- 네트워크 재조회가 실패해도 저장된 빠른 SBC 조건과 로컬 선수 캐시가 있으면 미리보기 제출안을 생성한다.
- 실제 제출 직전에는 Challenge를 다시 요청하고, 실패 시 현재 repository의 완전히 초기화된 Challenge만 대체 경로로 사용한다.
- 최종 제출 전 `challenge.canSubmit()` 검증은 항상 수행한다.
- 열기 실패 알림에는 설치 버전, `build`·`generate`·`render` 등 실패 단계와 오류 이름을 함께 표시하고 마지막 진단값을 Tampermonkey 저장소에 보관한다.

## 검증

2026-07-24 구현 시 다음 검증을 수행했다.

- 전체 userscript를 Node VM 파서로 문법 검사
- 최대 10개 제한: 후보 35명, 회차당 3명에서 10개만 생성
- 불완전안 제외: 후보 5명, 회차당 2명에서 완전한 2개만 생성
- 겹치는 조건: 제한 후보 2명과 넓은 후보 6명으로 두 개의 독립 제출안 생성
- 회차 간 모든 `item.id`가 고유한지 검사
- 동일 `databaseId`의 두 실물 복사본을 서로 다른 회차에서 사용 가능한지 검사
- 조건 간 `databaseId`가 겹치는 후보를 다른 회차에 재배치하는지 검사
- 재검증에서 사라진 카드와 회차 간 중복 안을 `invalid`로 전환하는지 검사
- 412×915, 360×720 모바일과 1024×800 데스크톱 모의 렌더링
- 세 화면 모두 가로 넘침 없음
- 좁은 모바일에서 선수 목록만 세로 스크롤
- 하단 제출 버튼과 상단 닫기·화살표가 목록과 겹치지 않음
- 이미 로드된 Challenge를 네트워크 요청 없이 재사용하는 경로
- `data.challenges`, `response.challenges`, 배열형 Challenge 응답 처리
- `success`가 생략된 응답과 repository 갱신 처리
- Challenge 재조회 실패 시 안전한 캐시 대체 경로
- 네트워크 로딩 실패 시 로컬 조건으로 미리보기를 생성하는 경로
- EA 네이티브 대화상자 없이 독립 오버레이를 생성하고 제거하는 경로
- 제출안 좌우 이동과 제출 버튼 클릭
- 닫기 버튼, 바깥 영역 탭, `Escape` 키 닫기
- 360×720, 412×915, 1024×800 시스템 Edge 오버레이 렌더링
- 모든 검사 화면에서 가로 넘침과 목록·하단 버튼 겹침 없음

실제 EA 계정에서의 최종 제출은 계정 아이템을 소모하므로 자동 테스트하지 않았다. 설치 후에는 저가 반복 SBC에서 제출안 선수와 실제 제출 선수가 일치하는지 먼저 확인해야 한다.
