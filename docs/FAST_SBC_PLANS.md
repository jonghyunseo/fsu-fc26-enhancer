# 빠른 SBC 제출안 설계

## 목표

기존 `Completion(n)`은 버튼을 누르는 즉시 선수를 다시 검색하고 한 번의 SBC를 제출한다. 새 동작은 제출과 선별을 분리한다.

```text
Completion
  → 제출안 생성
  → 최대 10개 목록 검토
  → 좌우 버튼으로 회차 이동
  → 현재 화면의 제출안만 제출
```

한 번에 열 개를 자동 제출하지 않는다. 사용자가 각 제출안의 선수를 확인하고 현재 안을 명시적으로 제출해야 한다.

## 제출안 개수

- 생성 상한은 10개다.
- 완전하게 채울 수 있는 제출안만 저장한다.
- 10개를 시도할 수 없으면 9, 8, 7 순서로 목표 개수를 낮춰 다시 배정한다.
- 반복 제출 가능 횟수에는 불완전한 제출안을 포함하지 않는다.
- 챌린지 모드에서 완성안이 하나도 없을 때만 진단용 부분안 한 개를 별도로 표시할 수 있다.
- `Completion` 가능 횟수 계산은 전체 제출 화면에서 `Math.floor`를 사용한다.
- 미할당 중복 선수 화면은 한 장의 중복 선수로도 빠른 SBC 진입점을 보여야 하므로 기존 `Math.ceil` 동작을 유지한다.

## 완성안 실패 진단과 부분 채우기

완성안을 만들지 못하면 후보 생성 실패를 하나의 일반 오류로 합치지 않고 가장 가까운 조합을 진단한다.

```text
진단용 부분 제출안
  → 선수 수, 팀 등급, 조직력 현재/요구 수치
  → 특수 카드·희귀도·OVR 조건 현재/요구 수치
  → 동일 리그·클럽·국가 조건 현재/요구 수치
  → 확정 후보 부족 또는 제한 탐색 실패 구분
  → 비어 있는 포지션을 카드 목록에 표시
  → 부분 스쿼드 채우기
```

정확도 수준은 다음처럼 구분한다.

- 후보 풀의 고유 `databaseId` 수가 요구 수보다 적으면 확정적인 후보 부족이다.
- 모든 선수를 높은 OVR 순으로 사용한 이론적 상한도 팀 등급을 넘지 못하면 확정적인 등급 부족이다.
- 포지션 최대 매칭으로도 채우지 못한 슬롯은 확정적인 포지션 후보 부족이다.
- 후보 수의 명백한 부족은 없지만 제한된 탐색에서 EA 검증을 통과하지 못하면 탐색 실패로 표시한다. 이 경우 재고 부족이라고 단정하지 않는다.

특수 그룹이나 최소 OVR 선수가 실제로 부족하면 논리적으로 필요한 최소 교체 선수 수만큼 일반 선수를 제거해 빈 슬롯으로 남긴다. 한 선수가 TOTW와 최소 OVR처럼 여러 조건을 동시에 만족할 수 있으면 같은 빈칸으로 묶고, 서로 다른 클럽이나 서로 양립할 수 없는 정확 OVR처럼 배타적인 조건은 별도 빈칸으로 계산한다. 같은 조건에서 두 장이 부족하면 한 카드가 두 번 기여할 수 없으므로 두 빈칸으로 계산한다.

호환 조건 묶음 탐색은 Android UI를 오래 막지 않도록 최대 5,000개 상태만 검사한다. 이 예산을 넘는 병적인 복합 조건에서는 조건별 최대 부족량이라는 증명 가능한 하한으로 돌아가며, 각 조건의 실제 부족 수치는 진단 행에 그대로 남긴다.

그룹 조건의 확정 부족, 모든 고평점 선수를 사용해도 넘지 못하는 팀 등급 부족도 최소 한 칸 이상의 교체 슬롯으로 표시한다. 명백한 수량 부족을 증명하지 못했더라도 EA 검증에 실패한 완전 후보를 유효한 스쿼드로 오해하지 않도록 최소 한 칸을 비운다. `최소 보충 슬롯`은 새 카드 하나가 여러 부족 조건을 함께 해결할 수 있다는 전제의 하한이며, 조건별 행의 `현재/요구` 수치가 실제 부족 내용을 나타낸다.

진단 수치는 빈칸을 만든 뒤 실제로 `부분 스쿼드 채우기`가 배치하는 선수만 기준으로 계산한다. 따라서 불완전 스쿼드의 팀 등급은 `—`로 표시되고, 빈칸 생성 전 가상 완성 후보의 등급·조직력은 후보 우선순위 계산에만 사용한다.

진단용 부분안은 `kind: "partial"`, `status: "partial"`, `verified: false`로 저장한다. 완료 가능 횟수에는 포함하지 않고 `Submit Plan`을 숨긴다. `부분 스쿼드 채우기`는 최신 Challenge의 조건 서명, 슬롯, 현재 잠금·보호 설정과 보유 상태를 다시 확인한 뒤 `slotIndex`에 보유 카드를 직접 배치하고 나머지를 `null`로 저장할 뿐 `submitChallenge()`를 호출하지 않는다.

## 선수 배정과 중복 규칙

서로 다른 식별자를 다른 범위에서 사용한다.

| 식별자 | 적용 범위 | 목적 |
|---|---|---|
| `item.id` | 모든 제출안 | 동일한 실물 카드를 둘 이상의 회차에 사용하지 않음 |
| `databaseId` | 한 제출안 내부 | 같은 선수의 다른 카드 버전이 같은 스쿼드에 들어가지 않음 |

SBC Storage에 동일 선수 카드가 두 장 있고 `item.id`가 서로 다르면 각각 다른 회차에 사용할 수 있다. 반대로 같은 `item.id`는 화면상 다른 조건을 만족하더라도 한 번만 예약한다.

후보에는 기존 빠른 SBC 보호 규칙을 적용한다.

- 잠금 선수 제외
- 사용자 지정 리그·희귀도 제외
- 거래 불가 우선 설정
- 대여, 진화 등록, 기간 제한 선수 제외
- 현재 활성 스쿼드 선수 제외
- 미할당 중복 선수에 대응하는 클럽 카드를 우선 배치
- SBC Storage 우선 설정 반영

기존 `getItemBy()`의 `firststorage` 처리는 `databaseId` 기준으로 후보를 하나만 남긴다. 제출안 생성에서는 서로 다른 실물 복사본을 다음 회차에 사용할 수 있도록 해당 중복 제거만 건너뛰고, Storage 우선순위는 별도 정렬로 적용한다.

## 배정 알고리즘

요구 조건별 후보를 만든 뒤 후보가 부족한 제한 조건부터 처리한다. 한 회차씩 전부 채우는 방식은 첫 회차의 넓은 조건이 다음 회차에 필요한 희귀 후보를 가져갈 수 있으므로, 모든 목표 회차를 함께 배정한다.

```text
목표 회차 N 결정
  → N개의 빈 제출안 생성
  → 제한적인 조건부터 처리
  → 조건 슬롯마다 후보가 가장 적은 회차를 먼저 선택
  → 다른 조건에도 필요한 databaseId는 뒤로 배치
  → item.id를 전체 회차 예약 집합에 추가
  → 한 회차라도 완성되지 않으면 N-1로 재시도
```

이 방식은 다음 사례를 처리한다.

- 희귀 1명과 동일 품질 나머지처럼 후보 조건이 겹치는 경우
- 동일 선수의 서로 다른 실물 복사본을 다른 회차에서 사용하는 경우
- 서로 다른 조건 후보가 같은 `databaseId`를 공유하는 경우
- 총 후보 수는 충분하지만 한 회차의 동일 선수 중복 때문에 배정이 실패하는 경우

## 평점·조직력 챌린지 제출안

기존 코드는 요구사항에 `TEAM_RATING` 또는 `CHEMISTRY_POINTS`가 있으면 `oneFillCreationGF()`의 결과를 강제로 비워 `Completion`을 만들지 않았다. 선수 한 명씩 검사하는 조건만으로는 팀 전체 평점과 조직력 충족 여부를 판정할 수 없기 때문이다.

`26.10.00`부터 이런 챌린지는 기존 `Calculate Score`를 유지하면서 같은 상단 빠른 작업 줄에 `Build Plans` 진입점을 별도로 표시한다.

```text
SBC 스쿼드 화면
  ├─ Calculate Score  → 기존 외부 평점 조합 계산
  └─ Build Plans      → 보유 선수로 제출 후보 생성
```

다음 조건을 해석할 수 있을 때만 `Build Plans`를 표시한다.

- 팀 평점
- 팀 전체 조직력
- 모든 선수의 최소 개인 조직력
- 특정 클럽·리그·국가/지역 선수 수
- 같은 클럽·리그·국가/지역 선수 수의 최소·최대·정확 조건
- 선수 최소 OVR·정확한 OVR
- 선수 품질·레벨
- 희귀도·희귀도 그룹

알 수 없는 요구사항 키나 값이 비어 있는 조건이 하나라도 있으면 진입점을 숨긴다. 일부 조건을 무시한 채 제출 가능한 것처럼 표시하지 않는다.

후보 생성 절차는 다음과 같다.

```text
Challenge 요구사항 파싱
  → 브릭 슬롯을 제외한 포메이션 위치 계산
  → 잠금·대여·진화 등록 등 보호 규칙을 적용한 후보 풀 생성
  → 리그·국가·클럽 중심 조직력 시나리오를 최대 16개로 제한
  → 포지션별 후보를 배치하고 개별 선수 조건 보정
  → 팀 평점 부족분 보정
  → 팀/개인 조직력 부족분 보정
  → 원본 Challenge를 복제한 virtual challenge에 배치
  → EA `meetsRequirements()`를 통과한 조합만 제출안으로 저장
```

후보 검색은 모바일 브라우저가 장시간 멈추지 않도록 네 개 시나리오와 각 회차 사이에 이벤트 루프를 양보한다. 후보가 많아도 시나리오는 16개, 제출안은 10개로 제한한다.

희귀 조건을 이미 만족한 회차에는 같은 조건의 선수를 불필요하게 더 쓰지 않도록 희소도 패널티를 적용한다. 따라서 첫 회차가 다음 회차에 필요한 희귀 선수를 모두 가져가는 것을 줄이고, 가능한 경우 10개 회차에 고르게 배분한다.

조직력 계산은 포메이션의 해당 위치를 수행할 수 있는 선수만 배치한 뒤 실행한다. 내부 계산 결과가 맞더라도 최종 저장 전 EA의 실제 요구사항 엔진으로 다시 검증하므로, 자체 계산과 EA 계산이 다른 조합은 목록에 들어가지 않는다.

### 최소 OVR 선수 보호

`26.10.01`부터 `85 이상 3명` 같은 최소 OVR 조건은 단순 충족 인원뿐 아니라 조건을 증명하는 선수들의 평점 초과량도 계산한다.

```text
85, 85, 85 → 최소 OVR 초과량 0
85, 86, 88 → 최소 OVR 초과량 4
88, 88, 88 → 최소 OVR 초과량 9
```

스쿼드에 조건을 만족하는 선수가 세 명보다 많으면 가장 낮은 세 명을 조건 증명 선수로 간주한다. 따라서 팀 평점에 필요한 별도의 고평점 선수까지 무조건 초과 사용으로 판정하지 않는다.

후보 생성은 다음 세 단계에서 고평점 재료를 보호한다.

1. 최소 OVR 인원이 부족한 동안에는 조건 평점과 정확히 같은 선수를 우선한다.
2. 개별 조건·팀 평점·조직력 보정에서는 최소 OVR 초과량이 늘어나는 교체에 패널티를 적용한다.
3. 유효한 스쿼드를 만든 뒤 높은 가치의 선수부터 더 저렴하거나 낮은 선수로 교체해 본다. 모든 조건을 다시 통과하는 교체만 확정한다.

선수 가치는 선수별 캐시 가격, 평점별 저가 기준표, `OVR × 1,000` 순서로 계산한다. 완성된 후보끼리는 예상 가치, 최소 OVR 초과량, 팀 평점 초과량, 전체 OVR 합계 순서로 비교한다.

다운그레이드 검사는 한 슬롯당 최대 24명의 후보와 최대 두 번의 반복으로 제한한다. 16번의 EA 조건 검증마다 이벤트 루프를 양보해 Android 브라우저가 장시간 멈추는 것을 방지한다. 교체 후에는 항상 virtual challenge의 `meetsRequirements()`를 다시 호출하므로, 전체 팀 평점이나 조직력 때문에 86·88이 실제로 필요한 경우에는 해당 선수를 유지한다.

이 과정은 모바일 실행 시간을 제한한 지역 탐색이다. 가능한 모든 선수 조합을 전수 조사하는 전역 최저가 보장은 하지 않지만, 완성된 조합에서 88을 85로 바로 교체할 수 있는 명백한 재료 낭비는 제거한다.

### 같은 리그·클럽·국가/지역 그룹 조건

`26.12.00`부터 EA의 다음 Challenge 요구사항 키를 지원한다.

| EA 요구사항 키 | 계산값 |
|---|---|
| `SAME_LEAGUE_COUNT` | 스쿼드에서 가장 많은 동일 리그 선수 수 |
| `SAME_CLUB_COUNT` | 스쿼드에서 가장 많은 동일 클럽 선수 수 |
| `SAME_NATION_COUNT` | 스쿼드에서 가장 많은 동일 국가/지역 선수 수 |

`SBCEligibilityScope.GREATER`는 최소, `LOWER`는 최대, 나머지는 정확 조건으로 변환한다. 예를 들어 다음 조건은 서로 독립된 고정 ID 조건이 아니라 스쿼드 전체의 그룹 빈도로 계산한다.

```text
같은 리그 최소 4명  → 가장 큰 리그 그룹 >= 4
같은 클럽 최소 2명  → 가장 큰 클럽 그룹 >= 2
같은 국가 최대 3명  → 가장 큰 국가 그룹 <= 3
```

후보 선택 점수는 아직 충족하지 못한 최소 그룹을 키우고 최대 그룹 초과를 피하도록 계산한다. 초기 선택 후에도 조건을 만족하지 못하면 선수 한 명씩 교체하면서 전체 그룹 위반량을 반드시 줄이는 교체만 허용한다.

그룹 조건 수리 중에는 이미 충족한 TOTW·희귀도·최소 OVR 같은 개별 선수 조건을 보존한다. 이후 평점과 조직력 보정에서도 그룹 조건을 다시 검사하고, 마지막에는 EA `meetsRequirements()`를 통과한 조합만 제출안에 저장한다.

`아무 TOTW/TOTS/FOF 최소 1명`처럼 여러 희귀도 그룹이 한 조건에 들어오면 그룹들을 AND가 아닌 OR로 판정한다. 즉 한 선수가 TOTW, TOTS, FOF 중 하나에만 포함되어도 조건 후보가 된다. 단일 그룹 조건은 기존과 동일하게 해당 그룹 포함 여부를 검사한다.

따라서 다음과 같은 복합 조건도 하나의 후보 생성 과정에서 함께 처리한다.

```text
같은 리그 최소 4명
같은 클럽 최소 2명
같은 국가/지역 최대 3명
TOTW 최소 1명
팀 등급 최소 75
총 조직력 최소 22
스쿼드 선수 수 11명
```

제출안 사이의 `item.id` 예약 규칙은 그대로 적용된다. 보유한 사용 가능 TOTW가 세 장이면 동일 TOTW 카드를 재사용하지 않고 최대 세 회차까지만 완전한 제출안을 만들 수 있다.

## 제출안 세션

생성 결과는 메모리의 제출안 세션에 보관한다.

```text
FastSbcPlanSession
  ├─ setId / challengeId
  ├─ estimatedCount
  ├─ requiredCount
  ├─ mode: simple | challenge
  ├─ challengeSpec
  ├─ currentIndex
  ├─ viewMode: list | grid (기본값: list)
  ├─ submitting
  └─ plans[]
       ├─ number
       ├─ kind: complete | partial
       ├─ status: ready | partial | filling | submitting | submitted | invalid
       ├─ itemIds[]
       ├─ slotItemIds[] (부분안에서는 null 포함)
       ├─ players[]
       ├─ snapshots[] (부분안에서는 null 포함)
       ├─ challengeSignature (부분안 생성 당시 조건·슬롯 서명)
       ├─ projectedSquadRating / projectedChemistry (후보 비교 전용)
       └─ diagnostics[]
```

팝업을 닫거나 보상 화면이 표시되어도 같은 SBC의 준비된 제출안은 세션에 남는다. 보상 화면의 `Again` 버튼은 준비된 제출안이 있으면 즉시 재선별하지 않고 제출안 화면으로 돌아간다.

## 정확한 제출과 재검증

제출 버튼은 현재 보이는 안의 `itemIds`를 그대로 사용한다. 제출 시점에 `getItemBy()`로 선수를 새로 선정하지 않는다.

1. Club과 SBC Storage에서 저장된 모든 `item.id`를 다시 찾는다.
2. 사라진 카드, 회차 간 중복, 회차 내부 `databaseId` 중복을 검사한다.
3. 최신 SBC Challenge를 다시 불러온다.
4. 저장된 선수 객체만 `playerListFillSquad()`에 전달한다.
5. `challenge.canSubmit()`을 다시 검사한다.
6. 검증된 현재 안만 EA 제출 서비스로 보낸다.

선수가 이동·소모되어 찾을 수 없거나 요구사항이 바뀌면 해당 안은 `invalid`가 되고 제출 버튼이 비활성화된다. `Regenerate Plans`로 현재 재고에서 다시 계산할 수 있다. 제출 요청 중에는 좌우 이동, 재생성, 제출 버튼을 모두 비활성화해 이중 탭을 막는다.

## Fill Plan과 Submit Plan

`Fill Plan`은 현재 후보를 SBC 스쿼드에 배치만 하고 제출하지 않는다. 버튼을 누르면 제출과 같은 방식으로 저장된 `item.id`, 회차 내부 중복, 최신 Challenge 요구사항을 다시 검사한다. 부분안은 생성 당시 조건·슬롯 서명과 최신 서명을 비교하고 현재 잠금·보호 설정에서 제외된 선수 또는 조직력이 필요한 슬롯의 부적합 포지션도 거부한다.

완성안은 후보 목록 순서를 Challenge 슬롯 순서로 유지한 채 기존 배치 경로를 사용한다. 부분안은 `null`을 포함한 11슬롯 배열을 전용 저장 경로로 전달한다. 이 경로는 EA `saveChallenge()` 응답과 `loadChallengeData()` 동기화가 끝날 때까지 기다리고, 명시적 저장 실패 시 기존 스쿼드를 복원한다. 서버 저장 성공이 확인됐지만 재조회만 실패한 경우에는 서버와 화면을 어긋나게 만들지 않도록 새 부분 스쿼드를 유지한다.

저장이 확인된 뒤에만 후보 팝업을 닫고 성공 알림을 표시한다. 어느 배치 경로에서도 `submitChallenge()`를 호출하지 않으므로, 사용자는 선수 배치와 빈칸·요구사항을 직접 확인한 다음 EA의 제출 버튼을 별도로 사용할 수 있다.

최신 재고나 요구사항이 달라졌다면 스쿼드를 채우지 않고 해당 후보를 `invalid`로 전환하며 팝업을 유지한다. 채우기 또는 제출 처리 중에는 좌우 이동, 재생성, `Fill Plan`, `Submit Plan`을 모두 비활성화해 중복 실행을 막는다.

- `Fill Plan`은 `Submit Plan` 바로 왼쪽에 배치한다.
- 카드 렌더러가 추가하는 가격, 메타, 포지션, 잠금 표식도 후보 영역에서는 숨긴다.
- 기본 `List` 보기는 구분선이 있는 짧은 세로 행을 사용한다.
- 각 List 행은 왼쪽 선수 카드, 가운데 `OVR + 이름`과 `포지션 · 희귀도 · 거래 상태`, 오른쪽 `클럽` 또는 `SBC 보관함` 배지로 구성한다.
- 순번은 표시하지 않고 OVR을 이름 바로 앞에 둔다. 긴 이름은 한 줄 말줄임으로 처리하며 저장 위치 배지를 밀어내지 않는다.
- 모바일 List 카드는 66×84px, 데스크톱은 72×90px 영역을 사용한다. 카드와 행 높이의 차이를 최소화해 선수 얼굴과 카드 디자인을 더 크게 확인할 수 있게 한다.
- `Grid`를 선택하면 상세 텍스트와 저장 위치 배지를 숨기고 선수 카드만 표시한다. 모바일은 한 줄에 3장, 데스크톱은 한 줄에 4장을 표시하며 카드 트랙 사이의 간격은 `0`이다.
- `List`와 `Grid` 전환은 기존 카드 뷰를 다시 만들지 않고 레이아웃 속성만 바꾼다. 선택은 현재 제출안 세션에서 유지되며 새 세션은 항상 `List`로 시작한다.
- 회차 이동이나 재생성으로 목록을 다시 그릴 때 기존 네이티브 카드 뷰를 해제해 메모리 누적을 막는다.
- 모바일은 화면 가장자리에서 6px 여백을 둔 전체 높이 팝업이다.
- 헤더와 하단 작업 영역은 고정되고 선수 목록만 스크롤된다.
- 보기 전환, 닫기, 좌우 버튼은 최소 40~44px 터치 영역을 사용한다.
- 데스크톱 팝업 폭은 최대 640px다.
- 제출안 화면은 EA 네이티브 대화상자 내부에 중첩하지 않고 `document.body`에 독립 모달 오버레이로 렌더링한다.
- 경고 대화상자의 종료 이벤트가 끝난 다음 이벤트 턴에 제출안 오버레이를 열어 Android Edge의 레이어 교체 충돌을 방지한다.
- 오버레이는 닫기 버튼, 바깥 영역 탭, `Escape` 키로 닫을 수 있다.

## 연결된 진입점

다음 `Completion` 버튼은 모두 제출안 화면을 연다.

- SBC 요구사항 화면의 빠른 완료 버튼
- SBC 상세 화면 상단 빠른 버튼
- 단일 Challenge SBC 타일
- 다중 Challenge 목록의 각 빠른 완료 버튼

미할당 중복 선수 화면의 빠른 작업 버튼은 기존 즉시 처리 경로를 유지한다. 이 버튼은 특정 중복 선수를 처리하기 위한 별도 흐름이며 `Completion` 미리보기 진입점이 아니다.

평점·조직력 챌린지는 `Completion` 대신 SBC 스쿼드 화면 상단의 `Build Plans`로 진입한다. 모바일에서 빠른 작업 버튼이 화면 폭보다 넓어지면 해당 한 줄만 가로 스크롤되며 피치나 하단 제출 영역을 밀어내지 않는다.

## SBC 데이터 로딩

제출안 미리보기와 실제 제출의 데이터 로딩 책임을 분리한다.

- 미리보기는 현재 화면에 이미 로드된 Challenge를 우선 사용한다.
- 캐시된 Challenge가 없으면 EA의 Challenge 목록과 상세 데이터를 요청한다.
- EA Web App 버전에 따라 Challenge 목록이 `data.challenges`, `response.challenges`, 최상위 `challenges` 또는 배열로 반환되는 경우를 모두 처리한다.
- 목록 응답의 `success` 필드가 생략되더라도 SBC repository가 정상 갱신됐다면 성공으로 처리한다.
- 네트워크 재조회가 실패해도 저장된 빠른 SBC 조건과 로컬 선수 캐시가 있으면 미리보기 제출안을 생성한다.
- 실제 채우기 또는 제출 직전에는 Challenge를 다시 요청하고, 실패 시 현재 repository의 완전히 초기화된 Challenge만 대체 경로로 사용한다.
- 진단용 부분안의 `부분 스쿼드 채우기`는 쓰기 직전 최신 Challenge 조회가 실패하면 캐시로 저장하지 않고 중단한다.
- 최종 채우기와 제출 전 `challenge.canSubmit()` 검증은 항상 수행한다.
- 열기 실패 알림에는 설치 버전, `build`·`generate`·`render` 등 실패 단계와 오류 이름을 함께 표시하고 마지막 진단값을 Tampermonkey 저장소에 보관한다.

- 그룹 조건을 위반한 초기 조합의 위반량을 4에서 0으로 줄이고 TOTW 1명을 유지하는 교체 수리
- `85 이상 3명`에서 85 세 장과 88 세 장의 최소 OVR 초과량을 각각 0과 9로 계산
- 전체 평점 85 조건에서는 88 세 장을 85 세 장으로 교체하고 예상 가치를 낮추는지 검사
- 전체 평점 87 조건에서는 88 두 장을 유지하고 한 장만 85로 낮추는지 검사
- 전체 평점 88 조건에서는 필수인 88 세 장을 임의로 낮추지 않는지 검사
- 새 세션의 기본 보기가 `List`이고 각 행에 카드, OVR, 이름, 포지션, 희귀도, 거래 상태, 저장 위치가 표시되는지 검사
- 360×720 및 412×915 화면에서 List 카드가 66×84px이고 여러 행이 같은 왼쪽 기준선에 정렬되는지 검사
- 긴 선수 이름에서도 오른쪽 `클럽`·`SBC 보관함` 배지가 밀려나거나 가로 스크롤이 생기지 않는지 검사
- `List`·`Grid` 전환 시 `data-layout`과 `aria-pressed`가 함께 바뀌며 카드 뷰가 재생성되지 않는지 검사
- Grid 전환 시 List 상세 정보가 숨겨지고 선수 카드만 남는지 검사
- 모바일 3열 114px, 데스크톱 4열 120px Grid와 계산된 카드 간격이 모두 `0px`인지 검사
- 후보 카드 안의 가격·메타·포지션·잠금 부가 표시가 모두 숨겨지는지 검사
- 회차 재렌더링과 팝업 종료 시 생성된 네이티브 카드 뷰가 모두 해제되는지 검사
- 네이티브 카드 생성 실패 시 수치 없는 카드 모양 대체 UI를 표시하는지 검사
- 최소 OVR와 특수 그룹의 부족을 한 선수가 함께 해결할 수 있으면 최소 보충 슬롯 한 칸으로 합치는지 검사
- 서로 다른 클럽, 양립할 수 없는 정확 OVR·최소 OVR, 일반 품질·특수 그룹 부족은 별도 보충 슬롯으로 분리하는지 검사
- 같은 리그 최소 인원과 이론적 팀 등급 상한의 확정 부족이 최소 보충 슬롯에 반영되는지 검사
- 포지션 한 칸이 비어 있어도 보유한 필수 TOTW·최소 OVR 카드를 부분 후보에 보존하는지 검사
- 불완전 스쿼드의 동일 클럽·리그·국가 최대·정확 조건을 완료로 오인하지 않고 확정 부족 상태를 유지하는지 검사
- 부족 조건 조합 탐색이 5,000개 상태 예산을 넘으면 증명 가능한 하한으로 종료하는지 검사
- 빈칸 생성 뒤 실제 선수 수·등급·조직력과 빈칸 생성 전 후보 비교용 예상치를 분리하는지 검사
- 부분 저장 Promise가 EA 저장과 재조회 콜백 전에 완료되지 않는지 검사
- 재조회한 11개 슬롯의 `item.id`가 요청한 부분안과 다르면 성공으로 처리하지 않는지 검사
- 명시적 저장 실패 시 기존 스쿼드와 저장 상태 플래그를 복원하는지 검사
- 서버 저장 성공 뒤 재조회만 실패하면 새 부분 스쿼드를 유지하는지 검사
- 요구사항 순서가 달라도 같은 Challenge 서명을 만들고 팀 등급·슬롯 변경은 다른 서명을 만드는지 검사

실제 EA 계정에서의 최종 제출은 계정 아이템을 소모하므로 자동 테스트하지 않았다. 설치 후에는 저가 반복 SBC에서 제출안 선수와 실제 제출 선수가 일치하는지 먼저 확인해야 한다.
